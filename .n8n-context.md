## Stack officielle
- Framework : Nuxt 3
- Langage : TypeScript strict (no any, strict mode activé)
- Architecture : Layer-based
- Package manager : pnpm
- Rendering : Hybrid (SSR + SSG selon la page)

### Modules autorisés
@nuxt/content, @nuxtjs/i18n, @nuxt/image, @nuxtjs/seo, @pinia/nuxt,
vuetify-nuxt-module, @unocss/nuxt, @vueuse/nuxt, dayjs-nuxt, nuxt-resend

### Interdictions strictes
- Axios → utiliser $fetch ou useFetch
- Vuex → utiliser Pinia uniquement
- Tailwind → utiliser UnoCSS
- Toute librairie UI supplémentaire (Vuetify est déjà en place)
- Abstractions génériques sans justification explicite

---

## Architecture layer-based

```
/components   → UI pure, présentation uniquement
/composables  → logique métier locale ou partagée (préfixe use obligatoire)
/stores       → état global Pinia uniquement si partagé entre pages
/pages        → routes, pas de logique métier
/layouts      → structure globale
/server       → API Nitro, validation stricte des entrées
/types        → types globaux PascalCase
/utils        → fonctions pures uniquement, aucun accès à l'état global
```

---

## Règles de séparation des layers

### Components
- Présentation uniquement
- Aucune logique métier complexe
- Props et emits strictement typés
- Maximum 200 lignes — au-delà, proposer un découpage

### Composables
- Préfixe `use` obligatoire (ex: `useProjectList.ts`)
- Logique métier isolée ou partagée
- Pas de dépendance directe au DOM sauf justification explicite
- Maximum 40 lignes par fonction interne

### Stores (Pinia)
- Uniquement si l'état est partagé entre plusieurs pages
- Actions simples et explicites
- Pas de logique métier lourde dans le store

### Utils
- Fonctions pures uniquement
- Aucun effet de bord
- Aucun accès aux stores ou composables

### Server (Nitro)
- Validation stricte de toutes les entrées
- Typage explicite des payloads et réponses API
- Jamais confiance au client

---

## Matrice composable vs store

| Situation                        | Composable | Store |
|----------------------------------|------------|-------|
| État partagé entre pages         | ❌          | ✅    |
| État local à une feature         | ✅          | ❌    |
| Logique métier isolée            | ✅          | ❌    |
| Données persistées cross-session | ❌          | ✅    |
| Appel API ponctuel               | ✅          | ❌    |
| Configuration globale app        | ❌          | ✅    |

Règle absolue : si l'état n'a pas besoin d'être global, il ne va pas dans un store.

## Conventions de nommage
- Composants : `PascalCase.vue`
- Composables : `useNomExplicite.ts`
- Types / Interfaces : `PascalCase`
- Variables et fonctions : `camelCase`
- Pas de `any`, jamais
- Strict mode TypeScript activé

---

## Patterns autorisés

### Toujours autorisés
- Composition API
- Dependency injection via composables
- Factory simple si duplication détectée
- Early return / guard clauses
- Mapping explicite plutôt que transformation implicite

### Acceptés si justifiés (demander avant)
- Singleton via store
- Abstraction générique
- Plugin global

### Interdits
- Service locator déguisé
- Logique métier dans les composants
- Abstraction prématurée
- Helper fourre-tout
- Couplage implicite entre layers

---

## Politique de refactorisation

Proposer un refactor si :
- Fonction > 40 lignes
- Composant > 200 lignes
- Logique dupliquée ≥ 2 fois
- Types implicites détectés
- Responsabilité d'un fichier floue

Méthodologie attendue :
1. Identifier le problème précis
2. Expliquer brièvement pourquoi c'est problématique
3. Proposer la version refactorisée
4. Maintenir la compatibilité de l'API publique

Pas de refactor silencieux.

---

## Tests attendus
- Composables : tests unitaires systématiques
- Stores : tests si logique non triviale
- API server : tests des routes et validations
- Composants : tests si comportement critique

Règles pour les tests :
- Isolés (pas de dépendances entre tests)
- Tester le comportement, pas l'implémentation
- Lisibles sans commentaires

---

## Performance
Secondaire après la lisibilité.
- Éviter les watchers inutiles
- Lazy load pour les composants lourds
- Favoriser SSG si le contenu est statique
- Ne jamais complexifier le code pour un gain marginal

---

## Sécurité
- Validation côté serveur obligatoire sur toutes les routes
- Sanitization si contenu externe injecté
- Typage strict des payloads API
- Jamais confiance au client

---

## Ce que le modèle DOIT faire

- Produire du TypeScript strict et lisible
- Respecter la séparation des layers sans exception
- Proposer des tests pour tout nouveau code
- Challenger les décisions si quelque chose viole les principes
- Montrer un diff clair avant/après pour toute modification
- Signaler toute violation de responsabilité détectée

## Ce que le modèle NE DOIT PAS faire

- Introduire une dépendance non listée dans les modules autorisés
- Créer un store sans vérifier que l'état est réellement global
- Modifier l'architecture existante sans demander confirmation
- Ajouter un plugin global sans justification
- Faire un refactor silencieux
- Utiliser `any` sous quelque forme que ce soit
- Mélanger logique métier et présentation dans un composant
