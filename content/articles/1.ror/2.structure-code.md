#### 📌 Vous utilisez une application Ruby on Rails en mode API ?

Alors, vous savez combien il peut rapidement devenir compliqué de gérer tout le code métier lorsque tout est regroupé dans les contrôleurs ou les modèles.

Pour garder votre code clair, simple à tester et à faire évoluer, il est vraiment conseillé de structurer votre projet de façon modulaire, en réservant à chaque type de logique sa propre place.

Dans cet article, je vous propose une organisation simple mais très efficace : utiliser des services pour les actions métier ponctuelles, des procédures pour coordonner plusieurs étapes, des forms pour valider les données en entrée, et d’autres dossiers spécialisés (jobs, mailers, queries, etc...) pour répartir les responsabilités.

Cette approche facilite la lecture du code, accélère les tests, et permet de réutiliser facilement vos composants, le tout dans une architecture orientée API.

##### 📂 Structure de l'application

L’architecture que je vous suggère repose sur une séparation claire des responsabilités.

Chaque type de logique trouve sa place dans un répertoire dédié, ce qui permet d’avoir un code lisible, facile à tester et simple à maintenir sur le long terme.

```bash
app/
├── controllers/          # Contrôleurs API, légers, appellent services/procedures
│   └── api/
│       └── v1/
├── models/               # Modèles ActiveRecord
├── serializers/          # Pour formater les réponses JSON (ActiveModel::Serializer, FastJSONAPI, etc.)
│   └── user_serializer.rb
├── services/             # Actions unitaires métiers
│   └── users/
│       └── create_user.rb
├── procedures/           # Enchaînement de services métier
│   └── onboarding/
│       └── register_user.rb
├── jobs/                 # Pour les traitements asynchrones
├── mailers/              # Pour les emails (même en API)
├── queries/              # Pour encapsuler les requêtes complexes
├── policies/             # Autorisation (Pundit ou maison)
├── forms/                # Objets de formulaire si besoin (ActiveModel)
├── presenters/           # (Facultatif) pour enrichir les données avant serialisation
└── validators/           # Validations personnalisées (ex: pour des schémas JSON)
```

```bash
app/
├── controllers/          # Contrôleurs API, légers, appellent services/procedures
│   └── api/
│       └── v1/
```

Les contrôleurs ne contiennent plus de logique métier.

Ils se contentent de recevoir les requêtes, d’appeler les procédures ou services appropriés, et de retourner une réponse JSON.

```bash
├── models/               # Modèles ActiveRecord
```

Les modèles restent liés aux entités de la base de données. Ils sont allégés au maximum en externalisant les validations complexes ou la logique métier vers d'autres couches (forms, services, validators…).

```bash
├── serializers/          # Pour formater les réponses JSON
│   └── user_serializer.rb
```

Les serializers (comme ActiveModel::Serializer, FastJSONAPI, ou Blueprinter) transforment les objets Ruby en formats JSON adaptés à l’API.

```bash
├── services/             # Actions unitaires métiers
│   └── users/
│       └── create_user.rb
```

Les services encapsulent une seule action métier cohérente, testable indépendamment.

Exemples : créer un utilisateur, envoyer une notification, appliquer une réduction.

```bash
├── procedures/           # Enchaînement de services métier
│   └── onboarding/
│       └── register_user.rb
```

Les procédures orchestrent plusieurs services dans une logique plus large.

Par exemple : l’onboarding utilisateur, qui inclut la création du compte, l’envoi d’un e-mail de bienvenue et la création d’un panier par défaut.

```bash
├── jobs/                 # Pour les traitements asynchrones
```

Les jobs contiennent les tâches longues ou non critiques à exécuter en arrière-plan via ActiveJob (par ex. envoi d’e-mails, export CSV, synchronisation externe...).

```bash
├── mailers/              # Pour les emails (même en API)
```

Même dans une API, des mailers peuvent être utiles pour les notifications (confirmation d’inscription, réinitialisation de mot de passe, etc.).

```bash
├── queries/              # Pour encapsuler les requêtes complexes
```

Les queries regroupent les accès complexes à la base de données (avec ActiveRecord, arel, ou raw SQL). Cela permet de nommer, tester et réutiliser des sélections spécifiques.

```bash
├── policies/             # Autorisation (Pundit ou maison)
```

Les policies centralisent les règles d'autorisation. Utilisées avec Pundit ou un système interne, elles gardent les contrôleurs et services focalisés sur leur rôle.

```bash
├── forms/                # Objets de formulaire si besoin (ActiveModel)
```

Les forms utilisent ActiveModel::Model pour valider les données complexes d’un formulaire ou d’un endpoint. Ils sont utiles lorsqu’on sort des simples validations ActiveRecord.

```bash
├── presenters/           # (Facultatif) pour enrichir les données avant serialisation
```

Les presenters servent à enrichir ou transformer les objets à exposer (ex : formatage HTML, calculs de champs, regroupement de données). Optionnels mais utiles quand les serializers deviennent trop lourds.

```bash
└── validators/           # Validations personnalisées (ex: pour des schémas JSON)
```

Les validators définissent des règles personnalisées réutilisables, en particulier pour les validations métiers, les structures JSON entrantes, ou des formats spécifiques (SIRET, IBAN, etc.).

Cette structure facilite le maintien d'un code métier indépendant du framework, ce qui le rend plus simple à tester en isolation et prêt à évoluer sereinement, sans risquer de créer de la dette technique.

##### 📂 Structure des tests

Pour accompagner une architecture bien organisée côté app/, la structure de test dans spec/ doit refléter cette séparation des responsabilités. Cela facilite le repérage, l'écriture et la maintenance des tests unitaires et d’intégration.

```bash
spec/
├── requests/            # Pour tester les endpoints (status + JSON)
│   └── api/
│       └── v1/
├── services/            # Tests unitaires des services
├── procedures/          # Tests unitaires des procédures
├── serializers/         # Tests des structures JSON (optionnel mais utile)
├── jobs/                # Vérifie que les jobs s'enquêtent bien
├── policies/            # Tests des droits
```

```bash
spec/
├── requests/            # Pour tester les endpoints (status + JSON)
│   └── api/
│       └── v1/
```

Les tests de requêtes couvrent les endpoints exposés par l’API : vérification des statuts HTTP, des structures JSON, de l’authentification et de la gestion des erreurs.

Ces tests se rapprochent du comportement réel côté client.

```bash
├── services/            # Tests unitaires des services
```

Les services étant des actions métier isolées, ils sont testés de façon unitaire : on vérifie l’effet attendu, les effets de bord (création d’objets, envois, etc.) et les cas d’erreur.

```bash
├── procedures/          # Tests unitaires des procédures
```

Les procédures orchestrant plusieurs services, leurs tests vérifient le bon enchaînement des étapes, la gestion des échecs partiels, et les effets globaux de bout en bout.

```bash
├── serializers/         # Tests des structures JSON (optionnel mais utile)
```

Ces tests assurent que les serializers produisent bien les bons formats JSON.

Cela permet d’éviter des régressions sur des structures exposées à des clients externes (frontends, partenaires, etc.).

```bash
├── jobs/                # Vérifie que les jobs s'enquêtent bien
```

On teste que les jobs sont bien déclenchés (avec have_enqueued_job, perform_enqueued_jobs, etc.), et qu’ils effectuent la tâche attendue sans effets indésirables.

On peut aussi vérifier leur gestion des erreurs.

```bash
├── policies/            # Tests des droits
```

Les policies définissent les règles d’accès.

Les tests vérifient que les bons rôles peuvent ou non effectuer certaines actions sur les ressources (lecture, écriture, suppression…).

#### ⚙️ Exemple concret : enregistrement d'un utilisateur

###### 1. Procedure : `procedures/onboarding/register_user.rb`

```ruby
module Onboarding
  class RegisterUser
    def initialize(params)
      @form = Users::RegistrationForm.new(params)
    end

    def call
      return Result.failure(errors: @form.errors.full_messages) unless @form.valid?

      user = Users::CreateUser.new(@form.attributes).call
      return Result.failure(errors: user.errors.full_messages) unless user.persisted?

      Result.success(data: user)
    end
  end
end
```

###### 2. Form : `forms/users/registration_form.rb`

```ruby
module Users
  class RegistrationForm
    include ActiveModel::Model

    attr_accessor :email, :password, :password_confirmation

    validates :email, :password, :password_confirmation, presence: true
    validates :email, format: { with: URI::MailTo::EMAIL_REGEXP }
    validates :password, confirmation: true

    def attributes
      { email: email, password: password }
    end
  end
end
```

###### 3. Service : `services/users/create_user.rb`

```ruby
module Users
  class CreateUser
    def initialize(attributes)
      @attributes = attributes
    end

    def call
      User.create(@attributes)
    end
  end
end
```

###### 4. Serializer : `serializers/user_serializer.rb`

```ruby
class UserSerializer
  include JSONAPI::Serializer

  set_type :user
  attributes :id, :email, :created_at
end
```

###### 5. Controller : `controllers/api/v1/users_controller.rb`

```ruby
module Api
  module V1
    class UsersController < ApplicationController
      def create
        result = Onboarding::RegisterUser.new(user_params).call

        if result.success?
          render json: UserSerializer.new(result.data).serializable_hash.to_json, status: :created
        else
          render json: { errors: result.errors }, status: :unprocessable_entity
        end
      end

      private

      def user_params
        params.require(:user).permit(:email, :password, :password_confirmation)
      end
    end
  end
end
```

##### 🔬 Tests

###### `spec/procedures/onboarding/register_user_spec.rb`

```ruby
RSpec.describe Onboarding::RegisterUser do
  let(:params) { { email: "test@example.com", password: "secret123", password_confirmation: "secret123" } }

  subject(:result) { described_class.new(params).call }

  it "creates a user successfully" do
    expect(result).to be_success
    expect(result.data).to be_a(User)
  end

  context "with invalid data" do
    let(:params) { { email: "", password: "123", password_confirmation: "456" } }

    it "fails with errors" do
      expect(result).to be_failure
      expect(result.errors).to include("Email can't be blank")
    end
  end
end
```

###### `spec/services/users/create_user_spec.rb`

```ruby
RSpec.describe Users::CreateUser do
  let(:attributes) { { email: "user@example.com", password: "password" } }

  it "creates a user" do
    user = described_class.new(attributes).call

    expect(user).to be_persisted
    expect(user.email).to eq("user@example.com")
  end
end
```

###### `spec/serializers/user_serializer_spec.rb`

```ruby
RSpec.describe UserSerializer do
  let(:user) { create(:user) }

  it "serializes the user" do
    json = described_class.new(user).serializable_hash

    expect(json[:data][:attributes]).to include(:email)
  end
end
```

###### `spec/requests/api/v1/users_spec.rb`

```ruby
RSpec.describe "User Registration", type: :request do
  it "registers a new user" do
    post "/api/v1/users", params: {
      user: {
        email: "api@example.com",
        password: "password",
        password_confirmation: "password"
      }
    }

    expect(response).to have_http_status(:created)
    expect(JSON.parse(response.body)).to have_key("data")
  end

  it "returns errors with invalid data" do
    post "/api/v1/users", params: { user: { email: "" } }

    expect(response).to have_http_status(:unprocessable_entity)
    expect(JSON.parse(response.body)).to have_key("errors")
  end
end
```
