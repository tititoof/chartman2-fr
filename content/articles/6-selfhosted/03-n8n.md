#### 🔗 n8n — L'automatisation, chez vous

Zapier, Make, IFTTT... les outils no-code d'automatisation sont très répandus, mais
tous partagent un point commun : vos données (et souvent vos identifiants
d'API) transitent par leurs serveurs.

n8n change la donne. C'est un outil d'automatisation de workflows open-source,
que vous pouvez héberger vous-même, avec plus de 400 intégrations natives et
la possibilité d'exécuter du code JavaScript ou des commandes système
directement dans vos workflows.

Concrètement, n8n vous permet de :

- 🔗 Connecter des dizaines d'API et services entre eux sans écrire de code
- ⚙️ Exécuter du JavaScript custom quand le no-code ne suffit plus
- ⏰ Planifier des tâches récurrentes (cron, webhooks, triggers)
- 🔒 Garder la main sur vos credentials et vos données d'exécution

Quelques exemples concrets de ce qu'on peut brancher derrière un workflow :

- 📄 Générer automatiquement des PDF
- 📧 Envoyer des mails
- 🤖 Piloter Ollama
- ☁️ Synchroniser Nextcloud
- 🎫 Créer des tickets Redmine
- 💬 Publier sur Discord
- 🐙 Automatiser GitHub

Le tout auto-hébergé, sans limite de workflows, sans quota d'exécutions
mensuelles.

> 💡 Le dépôt officiel :
> [github.com/n8n-io/n8n](https://github.com/n8n-io/n8n){:target="_blank"}


#### 🧩 n8n dans une stack qui a déjà Jenkins

Si vous suivez cette série, Jenkins gère probablement déjà vos pipelines
CI/CD : build, tests, déploiement. Une question revient souvent à ce
stade — pourquoi ajouter un second outil d'automatisation ?

Parce que Jenkins et n8n ne jouent pas dans la même cour :

- **Jenkins** excelle pour tout ce qui est *build et déploiement* : compiler,
  tester, packager, déployer un artefact. Son monde, c'est le code source et
  le pipeline.
- **n8n** excelle pour tout ce qui est *orchestration métier* : réagir à un
  événement, appeler des API tierces, transformer des données, notifier,
  synchroniser des outils entre eux. Son monde, c'est l'échange de données
  entre services.

Les deux se complètent très bien via de simples webhooks : Jenkins déclenche
n8n en fin de pipeline (notification, mise à jour d'un tableau de suivi,
déclenchement d'une action métier), sans que Jenkins ait besoin de connaître
les détails de cette action, et sans que n8n ait besoin d'accéder au dépôt
de code.

> 💡 Ici, on utilisera cette relation Jenkins → n8n comme exemple concret.
> Si vous n'avez pas encore Jenkins dans votre stack, vous pouvez adapter le
> déclencheur avec n'importe quel autre outil capable de faire un simple
> `curl` en fin de traitement.

C'est aussi cette logique de "brique d'orchestration" qui va me servir dans
un prochain article : un workflow n8n qui pilote un modèle **Ollama** en
local, pour automatiser des traitements de texte sans dépendre d'une API
externe. Depuis ses dernières versions, n8n propose également des nœuds IA
permettant de construire des agents, d'interroger des modèles locaux comme
Ollama ou des API externes, et d'enchaîner automatiquement leurs réponses
dans des workflows. Ce sera l'objet d'un article dédié — n8n installé
aujourd'hui posera les bases de cette intégration.

#### 🚀 Mise en place

##### 1. Créer la base de données interne de n8n

```bash
docker compose exec postgresql psql -U postgres
```

```sql
CREATE USER n8n_user WITH PASSWORD 'votre_mot_de_passe';
CREATE DATABASE n8n OWNER n8n_user;
GRANT ALL PRIVILEGES ON DATABASE n8n TO n8n_user;
\q
```

##### 2. Créer `.env-n8n`

Créez ce fichier à la racine de votre projet Docker, et ajoutez-le
immédiatement à votre `.gitignore` — il contient un mot de passe de base de
données.

```bash [.env-n8n]
# Application
N8N_HOST=n8n.domain.tld
GENERIC_TIMEZONE=Europe/Paris
TZ=Europe/Paris

# Base de données
DB_POSTGRESDB_DATABASE=n8n
DB_POSTGRESDB_HOST=postgresql
DB_POSTGRESDB_PORT=5432
DB_POSTGRESDB_USER=n8n_user
DB_POSTGRESDB_SCHEMA=n8n
DB_POSTGRESDB_PASSWORD=votre_mot_de_passe

# Runners & nodes avancés (utiles pour de futurs workflows, pas
# nécessaires pour l'exemple webhook de cet article)
N8N_RUNNERS_ENABLED=true
NODES_INCLUDE=n8n-nodes-base.executeCommand
NODE_FUNCTION_ALLOW_BUILTIN=fs,path,child_process
```

```bash
echo ".env-n8n" >> .gitignore
```

##### 3. Ajouter le service dans `docker-compose.yml`

```yaml [docker-compose.yml]
services:
  n8n:
    image: docker.n8n.io/n8nio/n8n
    restart: unless-stopped
    depends_on:
      - postgresql
    env_file:
      - .env-n8n
    environment:
      DB_TYPE: postgresdb
    volumes:
      - "./.docker/n8n/data:/home/node/.n8n"
      - "./Perso:/home/node/projets"
    labels:
      # Ajout dans traefik
      - "traefik.enable=true"

      # HTTP
      - "traefik.http.routers.n8n.rule=Host(`${N8N_HOST}`)"
      - "traefik.http.routers.n8n.entrypoints=http"

      # HTTPS
      - "traefik.http.routers.n8n-secure.service=n8n-secure"
      - "traefik.http.routers.n8n-secure.rule=Host(`${N8N_HOST}`)"
      - "traefik.http.routers.n8n-secure.entrypoints=https"
      - "traefik.http.routers.n8n-secure.tls=true"

      # Port interne
      - "traefik.http.services.n8n-secure.loadbalancer.server.port=5678"
    networks:
      projects_local_dev:
        aliases:
          - n8n.domain.tld

networks:
  projects_local_dev:
    external: true
```

##### 4. Démarrer le service

```bash
docker compose up -d n8n

docker compose ps n8n
docker compose logs -f n8n
```

L'application est ensuite accessible sur `https://n8n.domain.tld`. À la
première ouverture, créez votre compte propriétaire (owner).


#### 🪝 Premier workflow : enregistrer automatiquement les résultats d'un pipeline Jenkins dans Grist

Plutôt qu'une base de données dédiée, on va réutiliser l'API REST de Grist
(voir [l'article dédié](/blog/article/grist-self-hosted)) pour stocker le
résultat. L'objectif : à chaque fin de pipeline Jenkins, un enregistrement
est ajouté dans une table Grist "Builds" — sans base de données
supplémentaire, sans code, juste un webhook et deux nodes.

![Workflow](/img/content/n8n-basic-2.png){ width=100% }

**1. Créer le workflow dans n8n**

- **Node Webhook** : déclenche le workflow lorsqu'une requête HTTP `POST` est reçue sur le chemin `/webhook/jenkins-build`.

![Webhook](/img/content/n8n-basic-1.png){ width=100% }

- **Node Edit Fields (Set)** : en mode **Manual Mapping**, créer des champs plus simples à exploiter dans la suite du workflow.

![Webhook](/img/content/n8n-basic-3.png){ width=100% }

::tool-table
| Champ    | Valeur                    |
| -------- | ------------------------- |
| `job`    | `{{ $json.body.job }}`    |
| `status` | `{{ $json.body.status }}` |
| `build`  | `{{ $json.body.build }}`  |
::

- **Node HTTP Request** : envoie les données préparées à l'API REST de Grist afin d'ajouter une ligne dans la table **Builds**.

![Webhook](/img/content/n8n-basic-4.png){ width=100% }


n8n vous donne l'URL complète du webhook une fois le node créé, du type :
```
https://n8n.domain.tld/webhook/jenkins-build
```

> Pendant la conception du workflow, utilisez l'URL Test fournie par n8n. Une fois le workflow activé, utilisez l'URL Production, qui reste disponible en permanence.


**2. Appeler ce webhook depuis Jenkins**

Dans une étape `post` de votre `Jenkinsfile` :

```groovy
post {
  always {
    sh '''
      curl -X POST https://n8n.domain.tld/webhook/jenkins-build \
        -H "Content-Type: application/json" \
        -d "{\\"job\\": \\"${JOB_NAME}\\", \\"status\\": \\"${currentBuild.currentResult}\\", \\"build\\": \\"${BUILD_NUMBER}\\"}"
    '''
  }
}
```

**3. Le node HTTP Request vers Grist**

Le node reçoit les données du webhook (`{{ $json.job }}`, `{{ $json.status }}`,
`{{ $json.build }}`) et les envoie à l'API Grist :

- **Méthode** : `POST`
- **URL** : `https://grist.domain.tld/api/docs/{docId}/tables/Builds/records`
- **Header** : `Authorization: Bearer {votre_token_api_grist}`
- **Body** :
```json
{
  "records": [
    {
      "fields": {
        "Job": "{{ $json.job }}",
        "Statut": "{{ $json.status }}",
        "Build": "{{ $json.build }}"
      }
    }
  ]
}
```

Dans gris on peut voir quelque chose comme : 

::tool-table
| Job    | Statut  | Build |
| ------ | ------- | ----- |
| API    | SUCCESS | 145   |
| Site   | FAILURE | 146   |
| Docker | SUCCESS | 147   |
::

Cela conclut notre processus. À chaque terminaison de pipeline Jenkins, une entrée est automatiquement enregistrée dans Grist, offrant ainsi une consultation aisée, des filtres et des options d’exportation, sans nécessiter de modifications sur la base de données ni l’écriture de code d’intégration.

Ce même schéma (webhook → requête HTTP) peut être aisément réutilisé pour d’autres déclencheurs tels qu’un formulaire, une tâche planifiée (cron), ou un autre service au sein de la stack. 

Cette simplicité constitue la clé permettant de réaliser le workflow Ollama présenté dans un prochain article : réception d’un webhook en entrée, puis appel HTTP vers l’API Ollama en sortie.


#### 💾 Sauvegardes

Les workflows, credentials chiffrés et l'historique d'exécution de n8n sont
stockés dans PostgreSQL. Si Postgresus et RustFS sont déjà en place dans
votre stack, n8n est automatiquement intégré à votre stratégie de sauvegarde
existante.

> ⚠️ **Le point qu'on oublie souvent.** Les credentials stockés dans
> PostgreSQL sont **chiffrés**, et la clé de chiffrement ne se trouve **pas**
> dans la base de données — elle vit dans le dossier `.docker/n8n/data`.
>
> ```
> Base restaurée + clé de chiffrement perdue = credentials inutilisables
> ```
>
> Concrètement : si vous restaurez uniquement votre dump PostgreSQL après un
> crash, sans le volume `.docker/n8n/data`, tous les workflows et
> l'historique reviennent... mais chaque credential (accès API, SMTP,
> tokens...) devient illisible. Il faudra tous les ressaisir à la main.
> Sauvegardez ce dossier avec la même rigueur que la base de données —
> idéalement dans la même stratégie, pas à côté.

Les données métier, elles, n'ont même pas besoin de cette précaution ici :
elles vivent dans Grist, déjà couvert par sa propre sauvegarde.


#### 🔒 Sécurité — bonnes pratiques

n8n peut exécuter du code, appeler n'importe quelle API, et manipuler des
fichiers. Quelques réflexes simples limitent largement les risques :

- Ne jamais exposer le port `5678` directement sur internet
- Toujours passer par Traefik (reverse proxy), jamais d'accès direct au conteneur
- HTTPS obligatoire, sans exception, même en interne
- Créer un utilisateur Owner dès le premier accès, ne pas laisser l'instance sans compte
- Utiliser PostgreSQL plutôt que SQLite dès que l'instance est partagée ou en production
- Sauvegarder la clé de chiffrement (`.docker/n8n/data`) avec la même rigueur que la base
- Ne jamais stocker de tokens ou mots de passe en dur dans un node — toujours passer par les Credentials de n8n

C'est rapide à mettre en place, et ça évite l'essentiel des mauvaises
surprises.

#### ✅ Conclusion

n8n devient la brique qui relie les autres services de la stack sans les
coupler entre eux : Jenkins n'a pas besoin de connaître Grist, Grist n'a pas
besoin de connaître Jenkins, n8n s'occupe de la traduction entre les deux
via de simples webhooks et appels HTTP.

C'est exactement ce rôle de médiateur qui va être réutilisé dans le prochain
article pour connecter un workflow n8n à un modèle Ollama en local — la
suite logique de cette brique d'automatisation.
